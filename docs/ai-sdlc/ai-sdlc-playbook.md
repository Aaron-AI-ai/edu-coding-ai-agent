# AI-native SDLC 플레이북 정리

> 원문: [The AI-native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook) — Louis Claxton, Anthropic Applied AI, 2026-08-21
> 다이어그램: [`ai-sdlc-flow.html`](./ai-sdlc-flow.html) (원본 스펙 [`ai-sdlc-flow.workflow.json`](./ai-sdlc-flow.workflow.json))

## 핵심 메시지

- **이제 병목은 코드가 아니다.** AI로 코드를 쓰는 속도는 크게 빨라졌지만, 그 주변 프로세스(요구사항, 리뷰, 배포, 운영)는 그만큼 바뀌지 않았다.
- 그래서 SDLC 전체를 **커밋되는 산출물의 체인**을 중심으로 다시 짠다. 흐름은 일직선이 아니라 **루프**이고, 각 지점에 AI가 들어간다.
- **사람의 판단은 루프 위에 있고, 루프는 계속 돈다.** 기존 통제 목표는 그대로 두고, 이를 강제하는 방식만 새로 만든다.

```
intent.md → spec.md → plan.md → diff + 테스트 → PR 리뷰 결과 → 병합된 PR → 배포 → 인시던트 기록
                                                                                   └──→ 새 intent.md (루프)
```

모든 산출물은 git에 버전 관리된다. 그래서 커밋 SHA, 작성자, 시각, 수정 이력이 그대로 감사 추적(audit trail)이 된다.

## 6단계

| # | 단계 | 커밋 산출물 | 사람 게이트 | 다음 단계로 넘어가는 조건 |
|---|------|-------------|-------------|------------------|
| 1 | Plan | `intent.md` | 프로덕트 오너 승인 | intent 승인 |
| 2 | Design | `spec.md` | PO 리뷰, 위험도가 높으면 테크리드도 참여 | spec 승인 |
| 3 | Build | `plan.md`, diff, `CLAUDE.md` | 구현 전에 엔지니어가 plan 승인(고위험이면 아키텍트) | plan 승인 후 구현 |
| 4 | Test | 테스트 결과, 빌드 로그, 스크린샷 diff | 코드 소유자(검증 증거가 첨부된 상태에서 리뷰) | 테스트 통과, 빌드 성공 |
| 5 | Deploy | PR + 리뷰 결과, 승인 기록, 배포 로그 | 코드 소유자(branch 보호), 운영 배포는 릴리스 매니저 | 병합 → CI → 배포 |
| 6 | Maintain | 인시던트 기록, 포스트모템, 새 `intent.md` | 서비스 소유자 / on-call의 트리아지 | 이상 감지 → 1단계로 복귀 |

### 1. Plan — 아이디어를 바로 `intent.md`로
- 누군가 요구사항 문서로 정리해 줄 때까지 기다리지 않는다. 아이디어를 곧바로 `intent.md`로 캡처한다.
- 몇 주 걸리던 요구사항 도출이 몇 시간으로 줄어든다. PO 승인은 merge/close 기록으로 남는다.

### 2. Design — 요구사항과 설계를 한 세션에서
- 조직의 Skills(브랜드, 보안, 컴플라이언스, UX)가 이끄는 한 세션 안에서 요구사항과 설계를 함께 끝낸다.
- 정책을 나중 리뷰에서 "발견"하지 않고, spec을 쓰는 시점에 적용한다. 우려 사항은 해당 정책 오너에게 라우팅한다.

### 3. Build — plan mode가 기본
- **Plan mode**: 에이전트는 코드를 수정하지 않고 읽기만 한다. 엔지니어를 인터뷰한 뒤 `plan.md`를 작성하므로, 설계 리뷰가 코드 생성보다 먼저 일어난다.
- **`CLAUDE.md`**: 컨벤션, 명령어, 아키텍처, 반복되는 실수를 버전 관리되는 조직 지식으로 남긴다.
- **Skills**: 보안 표준, API 설계, 브랜드 규칙을 기계가 읽을 수 있는 형태로 둔다.
- **Hooks**: 보호된 경로를 막고, 포매터를 실행하고, 시크릿 유출을 방지하는 빌드 시점 가드레일이다.
- **병렬 세션 / 서브에이전트**: 엔지니어 한 명이 여러 작업 흐름을 동시에 관리한다.

### 4. Test — Claude가 스스로 검증한 뒤 넘긴다
- 테스트, 빌드, 스크린샷으로 피드백 루프를 주고, 에이전트가 사람에게 넘기기 전에 스스로 검증하게 한다.
- **CI의 지속 eval**: `CLAUDE.md`, Skills, Hooks가 바뀌면 에이전트 구성 자체를 회귀 테스트한다.
- **모든 운영 인시던트는 영구 eval이 된다.** 결과는 OpenTelemetry로 내보낸다.

### 5. Deploy — 게이트는 결정적으로
- **PR 리뷰 루프의 AI**: Claude가 들어오는 PR을 정책(버그, 보안, 컴플라이언스) 기준으로 리뷰하고, 자기 PR에 달린 코멘트도 직접 반영한다. 리뷰 정책은 `REVIEW.md`로 버전 관리한다.
- **승인 게이트로서의 Hooks**: 운영 배포, 보호된 경로 수정, 변경 관리 서명을 결정적으로 강제한다.
- **CI/CD 통합**: 파이프라인에서 Claude가 비대화형으로 판단 단계(트리아지, changelog, 수정)를 맡는다. 배포는 범위가 제한된 자격증명으로 MCP를 통해 한다.
- **티어별 자율성**: dev는 자유롭게 배포하고, staging은 그 중간, production은 게이트가 필수다. 에이전트는 자기 자신의 identity로 행동한다.

### 6. Maintain — 루프를 닫는다
- **결정적 모니터링**(모델을 쓰지 않음)이 관리 한계 이탈을 감지한다(예: CI 실패율 3σ). 그러면 headless Claude를 호출해 진단하고 수정안을 내게 한다.
- **정기 코드베이스 스캔**(Claude Security): 발견 사항은 검증한 뒤 보고한다. 패치는 PR 게이트를 거치고, 범위가 넓은 이슈는 `intent.md`가 된다.
- **Claude Tag on-call**: 인시던트 채널에 팀원처럼 참여한다. 진단, 승인, 수정이 모두 채널 기록에 남는다.
- 트리아지 결과는 **수정 PR** 또는 **새 `intent.md`** 가 되어 1단계로 돌아간다.

## 3단 통제 레이어

| 레이어 | 수단 | 성격 |
|--------|------|------|
| Advisory | Skills | Claude가 정책을 적용할 가능성이 높다. 위반은 드물지만 가능하다 |
| Deterministic | Hooks | 차단하거나 확인을 요청하며, 항상 강제된다. 결정이 로그로 남는다 |
| Gate | 사람 승인 | branch 보호, 릴리스 매니저 서명, 정책 오너 라우팅 |

**Managed Settings (플랫폼/IT 관리자)**: 시크릿 접근 차단, 네트워크 egress 제한, 안전한 inner-loop 명령 allowlist, OS 수준 샌드박스와 도메인 allowlist, 샌드박스 내 자격증명 제거, 모델 버전 하한, MCP·Skills·Hooks를 조직이 승인한 마켓플레이스로만 제한.

## 사람의 책임 (산출물별)

| 산출물 | 판단하는 사람 |
|--------|---------------|
| intent / spec | 프로덕트 오너, 아키텍트 |
| plan | 엔지니어 |
| PR | 코드 소유자 |
| 운영 트리아지 | 서비스 소유자, on-call |

## 측정 지표

- **선행 지표**: 산출물 커밋까지 걸린 시간, CI 첫 통과율, 첫 리뷰까지 걸린 시간, 발견 사항 중 실제 수정으로 이어진 비율
- **후행 지표**: 재작업 횟수, 운영까지 새어 나간 결함·취약점, 재발 인시던트, 변경 실패율
