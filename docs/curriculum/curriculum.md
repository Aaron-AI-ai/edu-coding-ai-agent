| 구성 | 내용 |
|---|---|

| API | 종목 목록, 기간별 시세 조회, 이동평균(MA5·MA20)·등락률 계산, 관심종목 등록 |

| 데이터 | 실제 일별 시세를 **사전에 받아 `data.sql`로 만들어 H2에 적재** (수업 중 외부 API 호출 없음 → 네트워크·인증·토큰 변수 제거) |

#### 시세 데이터 준비 방법 (강사 사전 작업)

- **1안(권장): KRX 정보데이터시스템 CSV 다운로드** — `data.krx.co.kr` → 개별종목 시세 추이에서 종목·기간 조회 후 CSV 다운로드 → `data.sql` 변환. 인증키·승인 대기 없이 종목 수만큼만 받으면 끝.
- **2안: KRX Open API** — `openapi.krx.co.kr`. 단 **기간 조회가 아니라 기준일자(`basDd`) 하루 단위**로 그날 전 종목을 받는 방식이라, 한 달치면 거래일 수만큼(약 20회) 반복 호출해야 한다. 인증키 발급 + **API별 이용신청 승인**이 모두 끝나야 하며(둘 중 하나라도 빠지면 401), 승인에 시간이 걸리므로 교육 전 미리 신청.
- **3안: 합성 데이터** — 실제 시세가 필수가 아니면 생성 스크립트로 만드는 쪽이 가장 깔끔하다. 라이선스 부담이 없고, 이동평균·등락률 테스트에 필요한 경계 상황(거래정지일, 급등락)을 의도적으로 넣을 수 있다.

**데이터 선정·배포 시 주의**

- KRX 데이터는 **비상업적 목적만 허용, 제3자 제공 금지, "한국거래소 통계정보" 출처 표시 필수** → 공개 레포 커밋은 피하고 사내 Git 사용, 필요 시 법무·컴플라이언스 확인.
- **수정주가 미적용** → 액면분할·병합 이력이 없는 종목으로 실습 종목 선정 (차트 단절 방지).
- 주말·공휴일은 데이터가 없는 것이 정상 → 기간 조회 테스트의 정상 케이스로 활용.
- 규모: 종목 5개 × 1년치 ≈ 1,250행. H2에 적재하기 적당하고 실습 중 조회도 빠르다.

### 2.3 한도 안전판 — 사용 크레딧 (강사 사전 작업)

- **좌석 유형 확인**: Standard는 Pro의 약 1.25배, Premium은 그 5배. 관리자 콘솔에서 확인하고, Premium이면 한도 우려는 사실상 해소된다.
- **Standard라면 교육 기간 한정으로 사용 크레딧(usage credits)을 활성화**한다. 한도에 도달한 수강생이 **환경을 바꾸지 않고** 계속 작업할 수 있고, 초과분만 과금된다. 1인당 상한을 함께 건다.
- 미리 다른 모델로 갈아타는 것보다, **한도는 그대로 쓰고 넘칠 때만 크레딧으로 넘기는 쪽**이 안전하다.

### 2.4 리허설로 실측 (필수)

Anthropic은 고정 수치를 공표하지 않는다. 실제 소모량은 대화 길이와 읽는 파일 양에 좌우되므로 **추정하지 말고 측정한다.**

- 교육 전 강사가 **Day 1·2 전체 실습을 Standard 좌석으로 완주**하며 모듈마다 `/usage` 기록.
- **M11 시연 사이클**은 강사 계정 소모량을 별도로 측정한다 (무인 실행 포함, 당일 재현 가능한지 확인).
- 반나절에 한도의 30% 수준이면 여유, 70%를 넘으면 실습 분량 조정 또는 크레딧 상한 상향.

### 2.5 수강생 공통 규칙 (Day 1 첫 시간에 배포)

비용뿐 아니라 **결과 품질**을 위해 지킨다.

- **모델**: 기본 `Sonnet`, 서브에이전트는 `Haiku`. Opus는 쓰지 않는다.

### 2.7 Java/Spring Boot 특화 절감 포인트

Java는 코드가 길고 Gradle 출력이 장황해 **같은 작업도 토큰을 더 쓴다.** 다음을 스타터 레포에 미리 반영한다.

- **프론트는 한 파일**: `index.html` + Chart.js CDN (빌드 도구·npm 없음 → 설치 대화 토큰 0).
- **Java LSP 플러그인(jdtls)**: 심볼 탐색을 grep·전체 파일 읽기 대신 LSP로 → 탐색 토큰 절감.

### M1. LLM이란 무엇인가 · 모델의 특성과 설정 (60분)

**LLM의 기본 동작 (20분)**

- 다음 토큰 예측이라는 단 하나의 원리
- 컨텍스트 윈도우 — 모델이 한 번에 볼 수 있는 범위, 넘치면 무슨 일이 일어나는가
- 도구 호출(tool use) — LLM이 "실행"하는 것이 아니라 "요청"하는 구조
- 그래서 생기는 한계: 환각, 최신 정보 부재, 긴 맥락에서의 누락

**모델 특성을 설정하는 방법 (20분)**

- `temperature` / `top_p` — 무작위성 조절. **단, 최신 Claude 모델(Sonnet 5·Opus 5 등)은 이 파라미터를 제거**하고 thinking·effort로 대체
- `max_tokens` — 출력 상한. 낮으면 문장이 잘린다
- **Extended thinking / effort** — 생각의 깊이를 조절하는 최신 방식 (`adaptive` thinking + `low`~`max` effort)
- 시스템 프롬프트 — 모델의 역할과 규칙을 고정하는 자리 (→ M2의 CLAUDE.md로 연결)

**모델의 형식과 구조 — 용어 정리 (20분)**

| 구분 | 의미 | 특징 |
|---|---|---|
| **Dense** | 모든 파라미터가 매 추론에 활성 | 구조 단순, 파라미터 수 = 연산량 |
| **MoE** (Mixture of Experts) | 전문가 여럿 중 일부만 활성 | 같은 크기 대비 추론이 빠르고 저렴, 대신 메모리는 전체를 적재 |
| **GGUF** | `llama.cpp` 계열의 단일 파일 모델 포맷 | 양자화(Q4_K_M 등) 내장, CPU·소형 GPU에서 로컬 실행 |
| **MLX** | Apple Silicon용 ML 프레임워크 | 통합 메모리 활용, 맥에서 로컬 모델 구동에 유리 |
| **양자화** | 가중치 정밀도를 낮춰 용량·메모리 절감 | 품질 일부 손실, 크기 대비 실행 가능성 확보 |

- 로컬 모델 vs API 모델을 언제 고르는가 — 보안·비용·품질·운영 부담의 트레이드오프
- 금융권 관점: 데이터 반출 제약이 있을 때 선택지가 어떻게 달라지는가

### M2. 하네스란 무엇인가 — Claude Code 구성 요소 (50분)

**모델을 감싸서 일하게 만드는 틀**이 하네스다. 같은 모델이라도 하네스에 따라 결과가 달라진다.

| 구성 요소 | 역할 | 언제 쓰는가 |
|---|---|---|
| **CLAUDE.md** | 항상 로드되는 프로젝트 규칙 | 빌드 명령, 레이어 규칙, 금지 사항처럼 **매번 필요한** 것 |
| **Skills** | 필요할 때만 불려오는 지식 묶음 | 특정 작업에서만 쓰는 규칙 — 호출될 때만 로드되어 토큰 효율적 |
| **Hooks** | 이벤트에 걸리는 결정적 자동화 | 위험 명령 차단, 편집 후 포맷, 종료 시 테스트 — **모델 토큰을 쓰지 않는다** |
| **Subagents** | 격리된 컨텍스트에서 일하는 하위 에이전트 | 긴 로그를 다루는 작업, 독립적인 작업 분리 |
| **Settings / 권한** | 무엇을 허용하고 무엇을 막을지 | `allow`/`deny`, 권한 모드(plan/acceptEdits 등) |
| **MCP · 플러그인** | 외부 도구 연결, 하네스 묶음 배포 | 문서 조회, 브라우저 검증, 팀 표준 배포 (M3) |

- 각 요소의 파일 위치와 형식, 로딩 시점(항상 vs 조건부)
- 흔한 실수: CLAUDE.md에 모든 것을 넣어 매 요청 비용을 올리는 패턴
- 사람의 역할 이동: 코드를 쓰는 사람 → **규칙을 설계하고 결과를 검증하는 사람**
- 강사 데모: 같은 요청을 하네스 적용 전/후로 실행해 차이 확인

   - 금융 계산 규칙: 가격·등락률은 `BigDecimal`(`double` 금지), `HALF_UP` 소수 2자리

2. **필수 스킬 구성 (25분)** — 예: `price-rules`(가격 계산 규칙), `api-scaffold`(Controller·Service·Test 뼈대)

4. **서브에이전트 설정 (20분)** — `test-runner`(Haiku): 테스트 실행 후 **실패 요약만** 반환

### M5. 실습 — 조회 API 개발 (80분) 🟡

**방금 만든 하네스로 기능 하나를 끝까지 만든다.** 코드는 직접 타이핑하지 않는다.

- 과제: **기간별 시세 조회 API** — `GET /api/stocks/{code}/prices?from=&to=`
  - 응답에 종가·등락률 포함, 기간 상한 검증, 데이터 없는 기간 처리
- 진행 순서
  1. 완료 기준을 먼저 제시 (통과할 테스트, 응답 JSON 형태)
  2. Plan Mode로 계획을 받고 **읽고 고친 뒤** 승인
  3. 실패 테스트 → 구현 → Stop 훅이 테스트 실행 → 통과
  4. 커밋
- 관찰 포인트: 하네스의 규칙이 실제로 지켜졌는가 (`BigDecimal` 사용, 반올림), 훅이 무엇을 잡아냈는가

- 리포트 항목 (`docs/day1-report.md`)
  - 구현한 기능과 API 명세, 통과한 테스트 목록
  - 내 하네스 구성: CLAUDE.md 규칙 / 스킬 / 훅 / 서브에이전트 각각 무엇을 왜 넣었는가
  - **하네스가 잡아낸 것**: 훅이 막은 시도, 규칙 덕분에 달라진 구현
  - **하네스가 놓친 것**: 내가 직접 지적해야 했던 부분 ← Day 2에서 고칠 목록

- 회고에서 2~3명이 발표 — 같은 과제에 서로 다른 하네스가 나온 이유를 비교

### M7. 루프 엔지니어링 · 그래프 엔지니어링 개념 (60분)

**루프 엔지니어링 (30분)**

- 에이전트 루프의 해부: 목표 → 탐색 → 계획 → 실행 → **검증** → 반복
- 루프가 실패하는 3가지 방식: 멈추지 않음 / 너무 일찍 멈춤 / 잘못된 것을 검증함
- **완료 기준(Definition of Done)을 먼저 주는 법** — "테스트가 통과하면 끝"이 왜 강력한가
- 피드백 되먹이기: 훅으로 검증 결과를 루프에 다시 넣기
- 사람이 개입할 지점 설계 — Plan 승인 게이트, 권한 모드
- **어제 리포트의 "하네스가 놓친 것"이 곧 루프의 결함이다**

**그래프 엔지니어링 (30분)**

- 한 줄 루프의 한계: 컨텍스트 오염, 긴 로그, 순차 처리의 느림
- **노드로 나누기**: 탐색 / 계획 / 구현 / 검증 / 리뷰를 분리하면 무엇이 좋아지는가
- **컨텍스트 격리**: 서브에이전트가 긴 로그를 대신 삼키고 요약만 돌려주는 구조
- **분기와 게이트**: 조건에 따라 갈리는 경로, 사람이 승인하는 지점
- **병렬**: 독립 작업을 동시에 — 언제 이득이고 언제 낭비인가 (비용 증가 주의)

### M8. 실습 — 나만의 루프 만들기 (40분) 🟡

**어제의 하네스를 "스스로 도는 루프"로 만든다.**

1. **완료 기준을 루프에 심기** — 어떤 명령이 통과해야 끝인지 CLAUDE.md·스킬에 명문화
2. **검증을 자동화** — Stop 훅이 테스트를 돌리고, 실패 시 그 결과가 에이전트에게 돌아가게
3. **노드 분리** — 테스트 실행·로그 요약은 `test-runner` 서브에이전트로 격리
4. **게이트 설정** — Plan 승인은 사람, 구현은 자동 (권한 모드·허용 목록 정리)
5. **어제 놓친 것 반영** — 리포트에 적은 결함을 규칙·훅으로 메우기

> **산출물**: 요청 한 번으로 계획 → 구현 → 검증 → 수정까지 도는 나만의 루프

### M9. 실습 — 루프로 기능 API 추가 구현 (50분) 🟡

**만든 루프를 실제로 돌려본다. 코드는 물론, 이번엔 중간 개입도 최소화한다.**

- 과제 (택 1)
  - ① 이동평균(MA5·MA20) 계산 API
  - ② 관심종목 등록·조회 API
  - ③ 등락률 상위 종목 랭킹 API
- 진행: 완료 기준 제시 → 루프 실행 → **끝날 때까지 지켜보기**
- 중간에 잘못 가면 **코드를 고치지 말고** 무엇이 부족했는지 기록 → 루프 요소를 고쳐 재실행

| 증상 | 고칠 곳 |
|---|---|
| 규칙을 어김 (`double` 사용 등) | CLAUDE.md 또는 스킬 — 규칙이 없거나 모호했다 |
| 같은 실수를 반복 | 훅 — 검증이 루프에 되먹여지지 않았다 |
| 엉뚱한 파일을 탐색하며 헤맴 | 구조 안내 또는 서브에이전트 분리 |
| 너무 일찍 끝냄 | 완료 기준 재정의 |

- 1차와 2차의 차이를 기록 — **무엇을 고쳤더니 무엇이 좋아졌는가**

### M10. AI-SDLC 개념 (80분)

- 전통적 SDLC와 무엇이 달라지는가 — 단계는 같지만 **수행 주체와 검증 방식**이 바뀐다
- 단계별 사람의 역할
  - Spec: 사람이 정의, AI가 구체화·질문
  - Plan: AI가 제안, **사람이 승인** ← 개입 비중이 가장 큰 지점
  - Implement: AI가 수행, 사람은 경계(권한·훅)만 관리
  - Verify: 테스트·빌드를 에이전트가 스스로 실행
  - Review/Release: AI 1차 리뷰 + 사람 최종 승인
- **"코드를 고치지 말고 하네스를 고쳐라"** — 오전 실습에서 몸으로 겪은 원칙의 일반화
  - 코드를 직접 고치면 그 자리만 해결되고, 규칙을 고치면 다음 실행부터 전부 해결된다
- 규모가 커질 때: 명세 → 계획 → 병렬 구현 → 통합 검증의 그래프
- 금융 도메인의 가드레일과 규제·감사 관점: AI 산출물의 책임 소재
- 도입 로드맵: 개인 → 팀 표준(플러그인 배포) → 조직 정책

### M11. 강사 시연 — AI-SDLC 한 사이클 관찰 (80분) 🔴

**토큰을 많이 쓰는 구간이라 강사 계정으로만 실행한다. 수강생은 관찰하고 질문한다.**

시연 흐름 — 요구사항 한 줄에서 PR까지

1. **명세 구체화** — 요구사항을 AI와 다듬어 완료 기준까지 도출
2. **Plan 도출과 승인** — 계획을 읽고 고치는 과정을 그대로 보여준다
3. **무인 실행** — Headless(`claude -p`) 또는 자동 승인 모드로 구현 위임
   - 경계 설정 시연: 권한 허용·차단 목록, 훅, `--max-turns` 상한, 로그 저장
4. **검증** — 테스트, `code-review` diff 리뷰, playwright로 화면 확인
5. **루프 강화 후 재실행** — 결함을 규칙으로 옮기고 같은 과제를 다시 실행
6. **병렬 그래프 시연** — 서브에이전트 + git worktree로 탐색·리뷰 동시 수행

관찰 포인트 (수강생 배포용 체크리스트)

- 사람이 개입한 지점은 정확히 어디였는가
- 에이전트가 헤맨 구간과 그 원인은 무엇이었는가
- 무인 실행에서 훅이 막아준 것은 무엇인가
- 1차 결과와 재실행 결과의 차이는 무엇이 만들었는가
- 이 사이클의 사용량은 얼마였는가 (`/usage` 공개)

### M12. 마무리 — 리뷰·PR·하네스 패키징 (40분) 🟢

- 최종 리뷰: `claude -p`로 금융 계산 규칙 체크리스트 리뷰 → 사람 최종 확인
- `commit-commands`로 브랜치 → 커밋 → PR 생성
- **하네스 패키징**: Day 1~2에 만든 CLAUDE.md·스킬·훅·에이전트를 `plugin.json`으로 묶어 팀 마켓플레이스에 배포 → 옆자리 수강생이 설치해 검증
- 발표 (팀당 5분)
  - 동작하는 화면과 구현한 API
  - 내 루프의 구조와 1차 vs 최종 실행의 차이
  - **무엇을 고쳤더니 무엇이 좋아졌는가**
  - 사용량과 남은 과제
